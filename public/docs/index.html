Getting started

A self-hosted WhatsApp bridge. Link a phone by scanning a QR, then send and receive messages over plain HTTP. Every account is a separate tenant with its own WhatsApp connection, its own contacts and its own API keys — no tenant can see another's data.

Base URL

…

Every path below is relative to this origin. The examples on this page are rewritten to use it, so you can copy them as-is.

Two credentials, one API Dashboard sessions send a Supabase access token; scripts and integrations send a long-lived API key. Both resolve to the same account, and every endpoint accepts either — except the admin routes, which require a real login.

Authentication

Send exactly one credential. If x-api-key is present it is used; otherwise the Authorization header is read.

Option 1 — API key x-api-key

Mint one in the dashboard or with POST /api/keys. The plaintext is shown exactly once and stored only as a SHA-256 hash, so a database leak does not expose usable keys. Keys start with wak_. 

…

Option 2 — session token Bearer

What the dashboards use. Sign in against Supabase in the browser, then send the resulting access token. Fetch the project URL and publishable key from GET /api/public-config — never hardcode them. 

…
Admin routes reject API keys /api/admin/* requires authKind: "session" and the admin role. A leaked client key must not be able to suspend accounts or delete other tenants, so it is refused with 403.

Recipient format

The to field accepts loosely formatted numbers and normalises them. Punctuation and spaces are stripped; a leading 00 dialling prefix is removed.

You sendBecomesNotes
"+91 98765 43210"919876543210@s.whatsapp.netPunctuation stripped
"919876543210"919876543210@s.whatsapp.netPlain digits
"0091987…"919876543210@s.whatsapp.netLeading 00 removed
"…@c.us"…@s.whatsapp.netLegacy server normalised
"…@lid"unchangedAlready a server identifier
"1234-5678@g.us"unchangedGroup JIDs are never rewritten
Include the country code A national number without it produces a syntactically valid JID that belongs to nobody — WhatsApp accepts the message and silently drops it. With VERIFY_RECIPIENT on (the default) every recipient is resolved through WhatsApp first, and an unreachable number is refused with 404 recipient_not_found instead of failing silently. Must be 7–15 digits.

WhatsApp session

Linking and unlinking the phone behind your account. One connection per account.

State machine idle → connecting → awaiting_scan → connected. Also logged_out (credentials wiped, a fresh QR is coming) and error (disconnected, reconnecting with backoff).
GET /api/session Current connection state

Never starts a connection. When no socket is running it answers from the stored row, with live: false — that is how you tell "offline right now" from "never linked".

Response 200

{
  "state": "connected",
  "connected": true,
  "user": { "id": "919876543210:12@s.whatsapp.net", "name": "Your Name" },
  "hasQr": false,
  "queued": 0,
  "live": true
}
POST /api/session/start Bring the connection up

Idempotent — returns the existing connection if one is already running. Responds 202 immediately; the socket finishes connecting in the background, so poll GET /api/session afterwards.

Response 202

{ "state": "connecting", "connected": false, "starting": true, "queued": 0 }

Returns 503 when the server is already at MAX_TENANT_SESSIONS and no idle socket can be evicted.

Sending

Requires a linked, connected session. Sends are queued and throttled per account.

Throttled on purpose Every send passes through a serial FIFO queue with a minimum gap of SEND_DELAY_MS (default 3000 ms) between two of your messages. WhatsApp bans accounts that fire messages back to back. A 202 means accepted and queued, not delivered. Past MAX_QUEUE_SIZE (default 500) you get 503.

Message operations

Acting on a message that already exists. The {id} in the path is WhatsApp's own message id — the id a send returned, or the id on a webhook payload — not a database id.

Two tiers, and the difference matters Reacting, deleting and pinning need only the message's key, which this server can rebuild from the id plus to — so they work on any message, however old. Replying (replyTo) and forwarding need the whole message, so they only work for the last 500 messages this process has seen. A restart clears that cache, and an older id returns 404 rather than sending something wrong.

Not supported, and why

Listed so you do not spend an afternoon looking for them. These are limits of what WhatsApp permits an unofficial client to do, not gaps waiting to be filled.

FeatureWhy not
Buttons, List, CarouselWhatsApp stopped honouring interactive templates from unofficial clients. They send without error and arrive as plain text, which is worse than refusing
Product, Catalog, OrderBusiness-catalog features, available only through the official WhatsApp Business Cloud API
Channels, Communities, StoriesExperimental and unstable in the underlying library; they break on WhatsApp's schedule, not ours
Group managementGenuinely possible — create, add, remove, promote, invite links. Simply not built yet
Forwarding an old messageNeeds the original message body. Only the last 500 this process saw are held; a restart clears them
If you need guaranteed interactive messages Use the official WhatsApp Business Cloud API. This service drives WhatsApp Web, which is the reason it is cheap and also the reason those features are out of reach.

Webhooks

Optional. Inbound messages are always stored in the database; set WEBHOOK_URL to also forward them to your own endpoint.

Delivery

POST with content-type: application/json and user-agent: sandesh/1.0. If WEBHOOK_SECRET is set it is sent as x-webhook-secret — compare it before trusting the payload.

Retries up to WEBHOOK_MAX_ATTEMPTS (default 3) with backoff of 500 ms, 1 s, 2 s… capped at 8 s. Retried on 408, 429 and any 5xx; any other 4xx is treated as a permanent rejection and dropped. Timeout is WEBHOOK_TIMEOUT_MS (default 10 s).

Your receiver cannot break the bridge Delivery is fire-and-forget and never blocks the message stream. A slow or dead receiver is logged and abandoned — messages still land in the database.

Payload

{
  "session": "sandesh",
  "id": "3EB0F3C7A1B2C3D4E5",
  "from": "919876543210@s.whatsapp.net",
  "fromNumber": "919876543210",
  "isGroup": false,
  "groupJid": null,
  "participant": "919876543210@s.whatsapp.net",
  "participantNumber": "919876543210",
  "pushName": "Asha",
  "timestamp": 1788862001,
  "type": "conversation",
  "text": "Hi, is this still available?",
  "receivedAt": "2026-09-08T11:14:07.412Z"
}

In a group, from/groupJid is the group and participant is the actual sender. In a 1:1 chat they are the same. timestamp is Unix seconds from WhatsApp; receivedAt is ISO-8601 from this server.

Not forwarded

Your own outgoing messages, status/story broadcasts, and protocol-only stanzas with no readable content.

Errors

Every failure returns the same JSON shape.

{
  "error": "recipient_not_found",
  "message": "919876543210 is not reachable on WhatsApp. If you left off the country code, add it (91 for India, so 91919876543210).",
  "details": { "number": "919876543210", "checked": true }
}

error is the stable machine-readable code — branch on it. message is written for a human and may change. details is present only when it adds something.

StatusCodeWhen
400bad_requestMalformed JSON, a missing field, or a value that failed validation
401unauthorizedNo credential, an expired session, or a revoked API key
403forbiddenNot an admin, an API key on an admin route, or a contact who opted out
404not_foundNo such route, or no such row of yours
404recipient_not_foundWhatsApp says that number is not reachable
409conflictAlready linked, or an admin guard would lock you out
502upstream_errorDatabase or WhatsApp failed the operation
503service_unavailableNot connected, queue full, session cap reached, or Supabase not configured
500internal_errorUnhandled — details are logged, never returned
Retrying 503 is worth retrying with backoff — it usually means "connecting" or "throttled". 4xx is not: the request itself needs to change.
